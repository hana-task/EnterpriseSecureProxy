# Defect Report

The solution was built from scratch. This report lists real defects found in our own code during development,
mostly in the code review at the end of each stage. Each one was fixed, and each fix has a test that fails
without it.

Paths are relative to `src/SecureProxy.Api/`. Tests are in `tests/SecureProxy.Tests/`.

| # | File/component | Observed behavior | Root cause | Risk/impact | Fix | Test |
|---|---|---|---|---|---|---|
| 1 | `Validation/` – `EnvelopeCheck`, `UrlIdCheck`, `ParameterCheck`, `DecryptionCheck` | JSON containing a lone surrogate such as `"\uD800"` (in a value or a property name) caused an unhandled exception instead of a rejection. | `JsonElement.GetString()` throws on a lone surrogate. Such JSON is syntactically valid, so `JsonDocument.Parse` accepts it. | 500 instead of 400 and no rejection reason in the audit. Breaks the rule that a check never throws. | `JsonObjectHelper.IsValidObject` reads all text once, in the envelope and in the decrypted content, and rejects it as `MalformedRequest` / `InvalidEncryptedPayload`. | `EnvelopeCheckTests.Invalid_text_is_rejected_instead_of_throwing`, `DecryptionCheckTests.Decrypted_content_that_is_not_a_json_object_is_rejected` |
| 2 | `Forwarding/UpstreamRequestBuilder` (base-path check) | The URL `/api-admin/x` passed the "stays under `/api`" check. | Prefix comparison as plain strings, without a `/` boundary. | A path template with `..` could reach a sibling path outside the destination's base path. | Compare against the base path followed by `/`. | `UpstreamRequestBuilderTests.Template_that_reaches_a_sibling_of_the_base_path_is_rejected` |
| 3 | `Forwarding/UpstreamRequestBuilder` | A path template containing `?` or `#` produced a broken URL (`?type=a?page=2`, or a query inside the fragment). | Only checked that the template starts with `/`. | Parameters reach the destination in the wrong form, or not at all. | A template with `?` or `#` is treated as `ProxyMisconfigured`. | `UpstreamRequestBuilderTests.Template_with_its_own_query_or_fragment_is_rejected` |
| 4 | `Security/Headers/ForbiddenHeaders` | `Content-Encoding`, `Content-MD5`, `Proxy-Connection` and `Expect` were forwarded if an operation's allowlist contained them. | Of the body headers, the fixed block list had only `Content-Length` and `Content-Type`. | The destination receives a header that does not describe the body the proxy built (for example gzip on plain JSON). | Block every `Content-*` header, plus `Proxy-Connection` and `Expect`. | `HeaderFilterTests.Hop_by_hop_headers_are_not_forwarded_even_if_the_allowlist_contains_them` |
| 5 | `Validation/DecryptionCheck` | A wrong authentication tag and a malformed payload returned different messages to the caller. | Two different message strings. | The caller can tell at which step decryption failed. | One message for every payload failure. The exact reason is kept for the audit only. | `DecryptionCheckTests.Caller_gets_the_same_message_for_a_wrong_tag_and_a_malformed_payload` |
| 6 | `Forwarding/UpstreamForwarder`, `Validation/OperationCheck` | A destination with a negative `TimeoutSeconds` threw `ArgumentOutOfRangeException` inside the forwarder, and its `CancellationTokenSource` was not disposed. A `MaxResponseBytes` ≤ 0 was noticed only after the destination had already acted. | The destination values were checked only by a database CHECK constraint, and `CancelAfter` was called before the `try`. | A bad row meant a 500 and a leaked resource. For a POST, the destination performed the action while the caller got 502. | `OperationCheck` rejects a timeout outside 1–300 seconds or a response limit ≤ 0 as `ProxyMisconfigured`, before forwarding. `CancelAfter` moved inside the `try`. | `OperationCheckTests.Destination_timeout_outside_the_allowed_range_is_rejected_before_forwarding`, `OperationCheckTests.Destination_response_limit_that_is_not_positive_is_rejected_before_forwarding` |
| 7 | `Validation/EnvelopeCheck` (reproduced against the real app) | A request with a malformed chunked body got 500 `internal_error`, and an error was logged. | Kestrel throws `BadHttpRequestException` while the body is read. `EnvelopeCheck` did not catch it, so it reached the global handler. | A caller's malformed request looks like our failure: 500 instead of 400, false alarms, no rejection reason in the audit. | Catch `BadHttpRequestException` while reading the body: `MalformedRequest` (400), or `RequestTooLarge` (413) when that is the server's status. | `EnvelopeCheckTests.Body_the_server_cannot_read_is_rejected_instead_of_throwing` |
| 8 | Handler of the `upstream` HttpClient (`Program`, `UpstreamForwarder.CreatePrimaryHandler`) (verified against a real server) | The destination received a `traceparent` header that is not on the allowlist, carrying a trace id the caller had sent. | .NET adds distributed-tracing headers to every outgoing request, and ASP.NET takes the trace id from the caller's `traceparent`. The recording test destination replaces this handler, so the tests did not see it. | A caller controls the value of a header that reaches the destination, against the allowlist (5.4), and can plant ids in the destination's monitoring. | `ActivityHeadersPropagator = DistributedContextPropagator.CreateNoOutputPropagator()`. The handler is created in one place. | `ProxyEndpointTests.Real_network_handler_adds_no_tracing_headers_and_follows_no_redirects` |
| 9 | `Errors/UnhandledExceptionHandler` (reproduced against Kestrel) | A PUT to the admin API with a body above `[RequestSizeLimit]` got 500 `internal_error`. | Kestrel throws `BadHttpRequestException` (413) while model binding reads the body, and the global handler turned every exception into 500. The fix in #7 covered only `EnvelopeCheck`. | A caller error looks like our failure: 500 instead of 413, false alarms. | `ProxyErrorCatalog.ForBadHttpRequest`: 413 → `request_too_large`, anything else → 400 `malformed_request`, without the server's message. | `UnhandledExceptionHandlerTests.Request_the_server_refused_to_read_is_a_caller_error_not_a_500` (plus a manual check against Kestrel) |
